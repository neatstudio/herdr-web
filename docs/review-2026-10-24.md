# herdr-web 全项目审查：安全、性能、逻辑

> 日期：2026-10-24。范围：当前**工作区**（含未提交的 `zerostack`/旧 herdr 兼容变更）、Go 服务、React 客户端、发布/部署脚本、已有文档。方法：静态调用链审查与现有用例阅读；未连接线上主机、未执行攻击验证或性能压测。**等级代表风险和优先顺序，不代表已在生产复现。**

## 结论先行

**架构方向有价值，但当前不宜把“私网 + 同源检查 + SHA-256”当成安全闭环。**核心风险是：高权限 API 无认证、发布源自己提供校验值、下载后直接运行文件验证版本，以及默认自动跟随。任务状态/并发有逻辑漏洞，看板和大文件有确定的扩展性瓶颈。建议先定信任边界，再决定是保留轻量控制台还是建设真正的分布式调度服务。

项目也有已经做对的部分：限制了监听地址，保护浏览器跨站写入，上传目录检查所有权/权限，文件预览限制常规文件并拒绝原始 SVG，更新拒绝“版本不更新”的文件并保留上一版。这些**不能取代认证和可信发布**。

## P0：阻止扩大部署

### SEC-01：未认证的更新链会运行由下载源提供的程序

**事实**：[请求守卫](../server/guard.go#L46-L68)明确允许没有浏览器来源头的请求；[更新入口](../server/selfupdate.go#L152-L179)接受请求里的 `from`，而 [fleet 自动跟随](../server/fleet.go#L576-L621)会从发现的 peer 找发布源。下载后版本和 SHA-256 都来自同一发布端；[验证逻辑](../server/selfupdate.go#L235-L333)把已下载文件改成可执行并调用 `binaryVersion`，[后者直接运行文件 `-version`](../server/selfupdate.go#L376-L392)。而且版本命令返回空字符串时条件 `got != "" && ...` 不会拒绝这个文件。

**影响与前提**：只要未获授权者能直连此 HTTP 端口，或同一尾网的某台机器/发布源被控制，就可能触发任意来源的代码在控制台服务账号下执行；无须等安装后的重启。“校验值匹配”只能证明下载与该来源自述一致。根用户服务风险更高。没有在真实机器上执行验证。

**修复方向**：负责人已确认“仅本人受控设备、仅人工更新”，短期应收紧访问并关闭自动跟随（需单独调整运行实例，本轮未操作）；后续用独立信任锚验证签名/固定可信摘要，仅允许明确来源，不运行未经认证的二进制；任何版本查询失败都拒绝安装。HTTP 验收：不可信或无认证发布源拒绝；失败不得调用文件、覆盖现有程序或重启。对应 [U-01～U-05](SPECS.md#4-spec-03-发布更新与回滚)。

### SEC-02：任何可达请求者可种入“可信”的发布内容

**事实**：`POST /release/*` 走[上传入口](../server/release.go#L91-L99)，[上传函数](../server/release.go#L246-L310)允许写发布文件与 `version`，写入后**服务器为收到的字节生成 `.sha256`**；相同端口还暴露本机文件预览、pane 输入、daemon 管理和任务启动。现有守卫不鉴别可达请求者身份（见 SEC-01）。

**影响**：受控发布者可以让跟随者接受与恶意文件一致的摘要；被触达的控制台还可被直接操作。该风险不依赖公网，只要求攻击者可以直连绑定的私网地址。已有边界只防止普通跨站网页直接发浏览器请求。

**修复方向**：发布/更新/进程控制接口与普通查看分开授权；最好使用离线或可信 CI 生成并签名的 manifest，机器只接受受信发布者签名；按 DEC-01 明确操作员权限边界。HTTP 验收：未经授权发布/读文件/写 pane 全部被拒绝，正常操作者保持可用。

## P1：优先修复

### SEC-03：未经验证的目标地址与更新来源可发起服务端请求

**事实**：[分发入口](../server/fleetjob.go#L179-L216)直接使用请求提供的 `targets`；[offer/start](../server/fleetjob.go#L568-L648)向这些 URL 发 HTTP 请求，[stop](../server/fleetjob.go#L665-L715)仅检查 `http(s)` 前缀、并不验证是否为已有任务和已知控制台；[hello](../server/fleet.go#L651-L690)接受调用方声称的 ID/地址并保存；[更新入口](../server/selfupdate.go#L152-L179)亦接受 `from`。`http.Client` 默认可跟随跳转，且这些地址不限制为本机已批准的 peers。

**影响**：具有调用权限的人可以让服务访问非预期的内网服务，任务正文也可能被发往错误的目标。受损 peer 还可能污染发现结果。这里的风险应和 SEC-01 一起解决，不能只检查 URL 字符串前缀。

**修复方向**：对 URL 做解析/归一化、校验目标是准入的机器或可信发布源，限制重定向，停止动作必须映射到实际分发记录，并结合鉴权；提供针对回环/非成员/跳转目的地的 HTTP 拒绝用例。

### LOG-01：任务容量和 taskId 的幂等判断不是原子操作

**事实**：[开始任务](../server/jobs.go#L86-L136)先查 `runningTask` 和 `runningCount`，经过多次 herdr 调用后才执行 [ledger.started](../server/jobs.go#L170-L217)。每次 ledger 查询单独加锁（[ledger.go](../server/ledger.go#L179-L224)），但没有“预留任务槽”的统一事务。

**影响**：两个同时到达的 `taskId` 相同的请求都可能看到“尚未启动”，各自创建 workspace；并发的新任务也可同时通过 `HERDR_WEB_MAX_JOBS=1` 门槛。此外，目标返回 HTTP 错误但工作区已经创建、而 ledger 尚未登记时，[市场分发](../server/fleetjob.go#L344-L371)查询不到运行任务可能尝试下一台。这违背 README 所说的“重试幂等 / 达上限返回 429”；现有用例只覆盖顺序调用。不能在没有全局协调的条件下宣称所有发起者共享“恰好一次”保证。

**修复方向**：任务创建前原子预留 `taskId` 与容量，失败/超时明确撤销或保留 `unknown`，重启时与 daemon 核对。HTTP 验收：同一机器并发同 ID 最多一次 workspace.create；不同 ID 不超过上限，跨机器不明结果不自动复跑。

### LOG-02：任务完成不会释放容量，失败创建可能留下无记录的 workspace

**事实**：[运行数](../server/ledger.go#L216-L225)是 ledger 中标为 running 的 workspace 数；[任务结束标记读取](../server/jobs.go#L355-L436)只在响应中返回 done/error，并不写入 `ledger.stopped`；[显式 stop](../server/jobs.go#L443-L465)才释放。`workspace.create` 后的 `agent.start/agent.prompt` 或当前工作区的 `runInPane` 失败时，直接返回错误而不记录已存在的 workspace（[jobs.go](../server/jobs.go#L141-L216)）。

**影响**：一次性任务做完后，默认上限 1 的机器仍可能报告“满”；失败创建后则可能留下未受计数/追踪的工作区。**“完成”和“关闭工作区”是两个不同概念**，最终如何计费容量须先确认 DEC-03。

**修复方向**：负责人已确认“完成即释放容量，保留结果/工作区”。定义独立的运行/完成/失败/未知状态，只有确定终态时释放执行槽，不能把暂时空闲当作完成；创建失败应返回可回收的工作区 ID 或有补偿动作。验收分别覆盖正常完成、命令失败、daemon 中途断开、人工关闭。

### LOG-03：`single` 没启动任务时前端仍按成功清空输入

**事实**：[市场分发](../server/fleetjob.go#L402-L410)在没有目标启动时以 HTTP 200 返回 `{ok:false, dispatch:...}`；[前端解析](../web/src/lib/herdr.ts#L663-L684)无条件重写为 `{ok:true,...}`；[发送表单](../web/src/components/DispatchSheet.tsx#L165-L190)不检查业务失败并清空 prompt。

**影响**：用户以为任务已发出，实际无人运行，重新输入正文有成本。HTTP 200 不是业务成功；前端必须尊重 JSON `ok`/逐机错误。

**修复方向**：保留服务端 `ok`；界面显示 decline/unknown 原因且保留表单。HTTP 验收：全拒绝、部分成功、网络不确定分别有不同反馈与响应字段。

### PERF-01：gzip 包装使本应流式传输的二进制进入内存

**事实**：[压缩中间件](../server/compress.go#L61-L80)只要请求带 `Accept-Encoding: gzip` 就先用 `compressRecorder` 缓存**完整响应**，之后才检查媒体类型/大小；它包装了所有路由（[bridge.go](../server/bridge.go#L861-L869)）。原始图片和发布文件虽使用 `ServeContent/ServeFile` 流式写入，但写入目标变成缓存器（[file.go](../server/file.go#L133-L169)、[release.go](../server/release.go#L111-L187)）。

**影响**：多个客户端下载大文件时，Go 进程内存峰值会随“文件大小 × 同时请求数”增长；对声称服务 1C/1G 的机器尤为危险。请求无 gzip 时不走此分支，未做压力测量。

**修复方向**：按路由/响应类型提前绕开压缩记录器，二进制始终流式；文本响应考虑流式压缩/有界缓冲。隔离环境用不同 Accept-Encoding、并发下载及内存峰值测量验收。

### PERF-02：看板查询逐条串行远程读状态与 git diff

**事实**：[任务列表](../server/fleetjob.go#L727-L775)对最多 20 条 dispatch 及其每个 job 逐个 `getJobStatus`，又逐个 `getJobDiff`；后者调用远端 git；整个请求有 30 秒上限。客户端打开面板时[每 5 秒](../web/src/components/DispatchSheet.tsx#L114-L129)触发一次查询，没有等待上次结束的门禁。

**影响**：一台慢机器即可拖慢后续所有任务的状态展示；超时后重复请求可能同时在路上。任务数量放大 RPC 和 git 调用成本。这是代码路径可推导的扩展风险，实际延迟需在慢链路复测。

**修复方向**：只拉取可见/活跃任务，限制并发并设置每目标短超时，结果可短期缓存；客户端避免重叠请求并在隐藏时暂停。HTTP 验收：慢机器不阻断其他结果。

## P2：应纳入近期整理

### PERF-03：ledger 启动时一次性读完整追加日志

[ledger.load](../server/ledger.go#L67-L86)使用 `os.ReadFile` 读取无限追加的 `ledger.jsonl` 并按行重放，虽然内存中的事件只保留 500 条，但持久文件没有轮换/快照。高频任务或 offer 后，启动成本会持续增加。建议用流式恢复+有界快照、明确历史保留策略；先测量再确定阈值。

### LOG-04：当前未提交的一次性任务完成标记可能丢失

`zerostack` 支持仍是本机未提交改动：[状态](../server/jobs.go#L355-L436)只读 `pane.read` 最近 200 行并在其中寻找末尾标记；一旦后续输出刷掉标记，状态会回到 running。当前用例只把短文本直接写进 fake daemon。建议使用 herdr 的终态/持久记录而非滚动窗口作为唯一事实来源；在单独测试环境覆盖长输出与重启。

### OPS-01：文档漂移和运维选项不一致

审查前 [README 前言](../README.md#L1-L32)称只访问本机 socket、没有持久状态；实际还有尾网心跳、发布下载和本地 `ledger.jsonl` / `dispatch.json`。本轮已修正前言，并在[旧版路由表](../README.md#L179-L211)加了指向完整索引的说明，尚未重写该表。[交接文档](../HANDOFF.md#L20-L76)包含日期较旧的机器状态，不能作为当前线上事实。`--jump` 在[参数解析之前](../scripts/deploy-remote.sh#L119-L145)设置 `ssh_opts`，解析参数后无重新设置，命令行 `--jump` 因而无效；HANDOFF 已记录此已知问题。

**方向**：以 [SPECS](SPECS.md) 为“要什么”的入口；[功能目录](../Fetures.md) 描述“现在能做什么”；交接文档只写带时间戳的观测；修好部署参数前采用 SSH config `ProxyJump`。

## 思路是否合理：三个必须说清的取舍

1. **“本人受控设备”不等于“所有尾网成员”。** 使用范围已确认是本人设备；轻量方案仍须严格限制网络 ACL 或验证机器身份。一旦有共享机器和供应链更新，它就不再只是本机 UI。
2. **“去中心化发现”与“去中心化信任”不是一回事。** 可以允许机器互相介绍地址，同时只接受由一个明确发布主体签名的版本。当前同伴既能推荐目标又能提供校验值，与“恶意 peer 不能伪造构建”的预期不符。
3. **“workspace 还在”与“任务正在消耗计算资源”不是一回事。** 已确认任务完成应释放容量但保留结果；执行容量、结果保留和人工关闭需拆开，避免卡住下一单或提前复跑。

## 推荐行动顺序（不擅自改生产）

| 顺序 | 工作 | 验收证据 |
| --- | --- | --- |
| 立即 | 落实已确认的“仅本人设备、仅人工更新”：收紧机器准入、关闭自动跟随，评估发布上传入口。**本轮未改任何运行实例**。 | 决策记录 DEC-01/02，网络/服务权限检查。 |
| 其次 | 建立可信更新、拒绝执行未验证二进制、限制目标/来源 URL 与跳转。 | 专用 `.env.test` 下 HTTP 状态码及 JSON 错误形状；失败后旧版仍运行。 |
| 再次 | 原子化任务预留和状态收敛，修前端 `ok:false` 反馈。 | 并发/异常/失败的 HTTP 契约测试；没有重复创建和假成功。 |
